## Critical context: the analytics system is much bigger than yesterday's plan assumed

Yesterday's session planned to "rotate the analytics sheet" as a quick fix. Reviewing the original March 12, 2026 build handoff revealed the system is comprehensive:

- **4 new files** (analytics cron, analytics API, analytics page, analytics CSS)
- **10 modified files** (auth.js, ops route, people route, directory route, dashboard route, cron daily route, analytics.js, TopNav, middleware, vercel.json)
- **~1,500 lines of code** total
- **28 instrumentation points** across 6 API routes (login event, page views, submissions, deletes, etc.)
- **Daily cron** runs at 8 AM CT, aggregates yesterday's events into 16 sheet tabs, posts Slack recap to `#intranet-recap`
- **Weekly cron** (Mondays) computes account scorecards, feature funnel, power users, device breakdown, ghost users, AI Pulse summary from Anthropic API, sends weekly email
- **Monthly cron** archives previous month's events to a per-month tab
- **Admin dashboard** at `/analytics` with Chart.js visualizations, scorecards, heatmaps, funnel charts, AI Pulse card

**Known issues in the original build (from handoff):**
- Device breakdown shows "Unknown" because `userAgent` wasn't wired through to `logEvent` calls
- Account scorecard partially works because not all `logEvent` detail objects include account context
- Monthly archive tab must be created manually in the sheet before the 1st of each month
- Weekly email requires Gmail domain-wide delegation, which may not be configured
- `CRON_SECRET` env var was never set — cron endpoints are currently open

**The real problem revealed yesterday:** The Google Sheet hit its 10,000,000 cell limit. Every `appendRow` call now returns:

```
{
  "code": 400,
  "message": "This action would increase the number of cells in the workbook above the limit of 10000000 cells.",
  "status": "INVALID_ARGUMENT"
}
```

The writes fail silently (caught and logged via `.catch()` per design), so the app keeps running. But every event from production is being dropped. Has been for an unknown duration.

**Decision made yesterday:** Don't rotate the sheet, don't delete the system. Feature-flag the writes off. Preserve the ~1,500 lines of work for Phase 3 (when analytics moves to Postgres anyway). Stop the bleeding immediately.

## Tomorrow's task in detail

### The change

Add an env var `ANALYTICS_ENABLED`. Guard the write functions in `src/lib/analytics.js` so they no-op when the flag is anything other than the string `"true"`. Default state: flag is `false` (or not set), writes are disabled.

### What to guard (write functions)

Based on the March 12 handoff, these are the analytics functions that write to the sheet:

- `logEvent(token, {...})` — User action logger (OAuth)
- `logEventSA({...})` — User action logger (service account)
- `logHealth(token, {...})` — API health logger (OAuth)
- `logHealthSA({...})` — API health logger (service account)
- `timedFetch(token, service, endpoint, fn)` — Wrapped fetch with auto-logging (OAuth)
- `timedFetchSA(service, endpoint, fn)` — Wrapped fetch with auto-logging (service account)
- `writeAnalyticsRow(tabName, rowData)` — Direct row append
- `clearAndWriteAnalytics(tabName, rows)` — Tab rewrite for weekly aggregations

Claude Code should confirm this list against the actual file — there may be additional functions added after the March 12 handoff.

### What NOT to guard (read functions)

These should continue working even when writes are disabled, so the dashboard still renders historical data:

- `readAnalyticsSheet(tabName)` — Reads any tab
- `slackRecap(text, blocks)` — Posts to Slack (no sheet write, separate concern)

### Cron behavior

Both `src/app/api/cron/analytics/route.js` and `src/app/api/cron/daily/route.js` should remain runnable. The aggregation logic reads events to compute summaries — when there are no new events, summaries should compute to zeros rather than crash. Claude Code should verify this.

### The env var

Add to `.env.local`:

```
ANALYTICS_ENABLED=false
```

Add to Vercel environment variables (Production, Preview, Development):
- Dashboard: `https://vercel.com/kitchfix-intranets-projects/kitchfix-intranet/settings/environment-variables`
- Key: `ANALYTICS_ENABLED`
- Value: `false`
- Environments: All three (Production, Preview, Development)

## Other things from yesterday worth knowing

### The /api/health middleware mystery (PR #6)

**What happened:** Built a new `/api/health` endpoint that should be publicly accessible for monitoring (Better Stack / Uptime Robot). Required adding `/api/health` to the middleware allowlist in `src/middleware.js`. Worked perfectly locally:

```
curl -i http://localhost:3000/api/health
→ HTTP/1.1 200 OK
→ {"status":"ok","hub_sheet":"reachable"}
```

But failed in production after merge:

```
curl -i https://kitchfix-intranet.vercel.app/api/health
→ HTTP/2 307
→ location: /login
```

Production was still gating the endpoint despite the middleware allowlist update. Reverted via PR #7 within 15 minutes.

**Hypotheses to investigate (Task 9, BLOCKED until this is understood):**
1. Vercel edge caching of middleware — old middleware still running despite the deploy
2. Next.js 16 middleware matcher configuration — maybe `/api/health` needs to be in a `config.matcher` export
3. Vercel-specific middleware execution order differs from local dev
4. The deprecated `middleware.ts` convention (warning observed in dev) might be related — Vercel might treat deprecated middleware differently than local Next.js does

**Investigation plan when you have time:**
- Check if `src/middleware.js` has a `config.matcher` export; if so, does it cover `/api/health`?
- Search Next.js 16 docs and GitHub issues for "middleware allowlist not working on Vercel"
- Consider whether Task 18 (middleware.ts → proxy.ts migration) needs to happen before Task 9
- Test a known-public route (e.g., `/api/auth/...` or `/api/cron/...`) on Vercel to confirm those allowlists actually work in production — narrows the problem space

**Do NOT re-attempt Task 9 until this is understood.** The change that broke production was small and well-reviewed, but landed broken anyway. The next attempt needs to be informed by what we learn about Vercel middleware behavior.
