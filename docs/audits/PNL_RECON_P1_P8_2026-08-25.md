## 0. Revision note (2026-08-25 same-day)

The first version of this audit reported Pattern A as "DB has no hourly labor for P1-P4 on 8 of 11 accounts - a structural gap driven by the 2026-04-20 daily-detail floor." **Kevin caught that claim and it was wrong.** The pre-floor hourly data DOES exist in `labor_actuals_latest`: **1,206 rows with `week_source = 'rippling_report'`, aggregate $862,457.61, across 9 accounts, spanning weeks 2025-12-29 through 2026-04-13** (verified by direct query in §14 below).

The reason those rows were invisible to the first audit: **every one of them carries `period_no = NULL`**. The v1 hourly probe aggregated by row `period_no`, and `Number(null)` failing the `1 <= p <= 13` filter meant every pre-floor row silently dropped. The salary probe used `periodOf(week_start)` and consequently reconciled across P1-P4 while hourly did not.

**This revision (v2):**
- Re-derives hourly period-attribution from `week_start` (same helper the salary probe uses).
- Rebuilds the recon summary, matrix, and variance list on corrected data.
- Rewrites §7 Pattern A (was a "structural gap"; actually a client aggregation bug).
- Revises the §13 verdict paragraph accordingly.
- Adds §14 as a defect log for the `period_no` NULL column on `rippling_report` rows (real data-integrity issue, deferred; not fixed tonight).

Prior audit's reconciliation counts were understated on hourly. Corrected counts and matrix follow.

## 3. Method

Three separate database queries, all filtered `fiscal_year = 2026`:

1. **Hourly budget:** `kpi_budgets` where `line_code = '3100.1'` and `account_key IN (11 accounts)`. Summed by (account, period_no).
2. **Salary budget:** `kpi_budgets` where `line_code = '3100.2'`. Same shape.
3. **Hourly actuals:** `labor_actuals_latest` `amount` column, filtered `fiscal_year = 2026`, aggregated by (account_key, period_no). `period_no` is a column on the row so no client-side derivation.
4. **Salary actuals:** `labor_salary_actuals` `amount`, filtered `week_start` in FY2026 (2025-12-29 through 2026-12-27). No `period_no` on this table; derived client-side via `periodOf(week_start)` from `src/app/kpi/labor/lib/periods.js`.

**v2 correction:** hourly actuals now also derive period via `periodOf(week_start)`. The v1 aggregation grouped by row `period_no`, which is NULL on all 1,206 pre-floor `rippling_report` rows. Same helper as salary now, consistent with the file's period assignment (§14 defect log).

**Classification tolerance:**

- **RECON** = `|delta| <= $1.00` (absorbs rounding: P&L Actual columns round to whole dollars, DB carries cents; a $0.02 delta on a salary annualisation is arithmetic parity, not a variance)
- **MIDBAND** = `$1.00 < |delta| <= $100 AND <= 1%`
- **SIGNIFICANT** = `|delta| > $100 OR > 1%` (Kevin's variance bar)

**Null handling:** both sides null OR one side null + the other `|v| <= $1` = RECON. One side null + the other > $1 = SIGNIFICANT.

**Deliberately out of scope:** the API / rendering layer. Kevin's spec says "check second, and only for accounts where the DB reconciles" - this pass verifies DB vs finance only. If a rendering defect exists on top of a reconciled DB, it needs a separate on-prod inspection pass and is noted at the end.

**Class of defect**: any query that aggregates hourly actuals by `labor_actuals_latest.period_no` silently loses ~a third of the FY table on the affected accounts. `Number(null)` returns `0`, which falls outside the `1 <= p <= 13` guard used by most probes and by the audit's own v1 script - so the rows do not surface as errors; they simply disappear.

**Consequence in v1 audit**: the entire Pattern A finding ("DB has no hourly labor for P1-P4 on 8 of 11 accounts - structural, known") was manufactured by this bug. The data was in the table; the aggregation dropped it. See §7 Pattern A for the retraction and §0 for the correction workflow.

**Consequence in the rendered board**: unknown from this audit. The board's period-aggregation code path is a separate check. If the board uses the same groupby-`period_no` shape, the same rows are missing from what users see; if it uses `periodOf(week_start)` (like `labor_salary_actuals` does), the rows render correctly.

**Fix candidates** (deferred - Kevin's ruling: log tonight, do not fix tonight):

1. **Backfill the column**. One-off UPDATE on `labor_actuals_latest` deriving `period_no = periodOf(week_start)` for the 1,206 affected rows. Reversible, targeted, no schema change. Preferred if row-level `period_no` is a load-bearing contract downstream.
2. **Fix the loader**. Whatever pipeline writes `week_source='rippling_report'` rows needs to compute `period_no` at insert time. Prevents recurrence but leaves existing rows null unless combined with #1.
3. **Drop the column and require callers to compute**. If nothing downstream actually needs a row-level `period_no` column (the fiscal-period is a function of `week_start`, so it's derivable), remove the column and force every caller to use `periodOf(week_start)`. Highest cost, strongest guarantee.

**Audit follow-up before any board-facing claim about pre-floor coverage**: grep the codebase for any `.select("...period_no...")` or `.eq("period_no", ...)` on `labor_actuals_latest`. Every caller is a potential silent-drop site. This audit's v1 was one such caller; there may be others.
