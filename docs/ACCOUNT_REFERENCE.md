## How to read this

Every value carries a confidence marker:

- `[verified - <check>]` - the check that established it, named. `128/128 workers at Goodyear via /workers endpoint` is a verified.
- `[inferred - <basis>]` - read from a name, a convention, or a single sample. Reasonable, unproven. **Read this column hardest.**
- `[unknown]` - not derivable from data, needs an owner ruling.
- `[conflict - src1: X, src2: Y]` - two sources disagree; both shown, no side picked.
- `[absent - 0 rows]` - queried, table returned no rows for this account (may be by design: D26 salaried-only, D17 CORP-out-of-scope, or no volume yet).

**Do not treat "inferred" as "probably fine."** The `- REDS` error was an inferred value that read as obvious. Every subsequent `[inferred]` cell is a candidate for the same failure.

## Section 5 - Systems we have not touched

### Account identity currently inferred at runtime (the finding this document exists to eliminate)

Runtime inference is anywhere production code resolves an account by parsing a string rather than reading an explicit table. Every entry below is a candidate for a mapping-table fix.

Grepped for the pattern on 2026-08-05 across `src/`, `scripts/`. Four sites found. The Rippling MLB Stats claim in the previous draft was wrong - the resolution IS an explicit table (`TRACKED_TEAMS` in `src/lib/scheduleDrift.js:34-46`), a well-designed example rather than a defect. Correction below.

#### 1. Invoice folder resolution collapses TXR-TX-H and TXR-TX-V into one folder

**Location:** `src/lib/drive.js:54` [code-read]

```js
async function ensureInvoiceFolder(drive, account) {
  ...
  const accountShort = account.split(" - ").slice(0, 2).join(" - ").trim();
  const yearFolderId = await getOrCreateFolder(drive, INVOICE_DRIVE_FOLDER_ID, year);
  const monthFolderId = await getOrCreateFolder(drive, yearFolderId, month);
  const accountFolderId = await getOrCreateFolder(drive, monthFolderId, accountShort);
```

**What it parses:** account `team_key`. Takes the first two segments after splitting on ` - `.

**What breaks:** for accounts with a three-segment key, only the first two survive.
- `CIN - AZ` → `CIN - AZ` (correct)
- `TXR - TX - H` → `TXR - TX` (drops the `H`)
- `TXR - TX - V` → `TXR - TX` (drops the `V`)

**Consequence:** invoices for TXR-TX-H and TXR-TX-V land in the same `2026/08/TXR - TX/` Drive folder. No way to tell from the folder structure which side an invoice belongs to. Any downstream code that reads the folder to determine the account gets ambiguity.

**Fix:** use the full `team_key` as the folder name, or resolve to a per-account folder ID via a mapping column on `accounts`.

#### 2. Vendor ID composition has the same TXR-TX-H/V collapse

**Location:** `src/lib/dataStore/vendor.js:174` [code-read]

```js
return `${vendorId}_${String(accountKey || "").split(" - ").slice(0, 2).join("-")}`;
```

**What it parses:** the same `account_key`, same two-segment slice.

**Consequence:** vendor IDs constructed for TXR-TX-H and TXR-TX-V are identical when the same vendor is scoped to both sides. If vendors are per-side, one side's vendor overwrites the other.

**Fix:** same as above - use the full key, or lookup by account-key-to-vendor-scope mapping.

#### 3. People module location parsing (probable H/V collapse)

**Locations:**
- `src/components/people/PAFForm.js:70` [code-read] - `const segments = locationKey.split(" - ");`
- `src/components/people/AdminQueue.js:604` [code-read] - `const teamAbbr = item.location.split(" - ")[0];`

`AdminQueue.js:604` takes only the FIRST segment (`TXR` for both H and V) which is coarser than the drive/vendor cases but same class of failure. Worth Kevin checking whether these are display-only (probably fine) or attribution-affecting (would need the same fix).
