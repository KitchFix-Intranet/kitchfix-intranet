# Section G: Postgres inventory

## Method

- **Migrations read** from `docs/migrations/` (119 SQL files, 108 `CREATE TABLE` statements) to establish schema origin, purpose, and design notes.
- **Live metadata** pulled via Supabase MCP against project `dhkhvaokmtsfscnwnbum` (KitchFix-Intranet) using `list_tables` (public schema, live row counts) plus one `information_schema.tables` query and one aggregate `SELECT count(*)` against two views. **Row counts are LIVE** as of 2026-08-31 for all base tables; also live for the two views that showed up as non-tables (`user_accounts_derived` = 35, `rippling_raw_workers_latest` = 1129). No writes issued.
- **Code sites** located via `grep` for `from("<table>")` under `/src/`. "Read from" and "Written from" columns list up to 3 example files (usually API routes or dataStore modules); the full call graph is broader. `dataStore/opd.js` is the single Postgres orchestrator for the OPD tables; the Playbook UI client and admin client both go through `/api/playbook/route.js`, they do not touch Supabase directly.
- Only tables **plausibly in scope for OPD or Academy** are enumerated below. SC (spend/labor/sc_*), invoice/AP (billcom, ai_line_items, gl_codes, invoice_*), inventory (count_*, inventory_items, item_aliases, storage_locations, price_history, review_queue, merge_history*), KPI (kpi_*), Rippling raw tables, and vendor tables are OMITTED unless they double as an identity/roster/access source Academy would need.

## Name collisions (Academy wants X, occupied by Y)

- **`users`** - `public.users` exists (0 rows, no writers, no readers - legacy/orphan). `auth.users` is the Supabase-owned auth table. Academy should NOT reuse `public.users`; either drop the orphan first or namespace (e.g., `academy_learners`).
- **`credentials`** - collides with `auth.webauthn_credentials` naming space. `public.credentials` is unclaimed; safe if used. Recommend prefix (e.g., `academy_credentials`) to keep the auth-vs-app boundary readable.
- **`sessions`** - `auth.sessions` occupies the name in the auth schema. `public.sessions` is unclaimed but visually confusing next to `auth.sessions`. Recommend `academy_sessions` if the concept lands.
- **`one_time_tokens`** - `auth.one_time_tokens` occupies the auth schema. `public.magic_links` / `public.one_time_tokens` are unclaimed. Same recommendation: namespace.
- **`identities`** - `auth.identities` (Supabase). `public.identities` unclaimed.
- **`questions`** - `public.sousai_questions` occupies the "questions" concept for the AI question-log (chat asks, not quiz questions). `public.questions` bare name is unclaimed but semantically loaded now - an Academy "quiz question" table should use `academy_questions` to avoid confusion with the SousAI ask-log.
- **`documents` / `document_*` / `document_chunks` / `document_pins` / `document_content` / `document_relationships` / `document_surfaces` / `document_issues`** - the entire `document_*` family is owned by OPD (Playbook + SousAI retrieval). If Academy wants to add lesson-content-flavored tables it must NOT reuse the `document_*` prefix. Recommend `academy_*` prefix for everything (`academy_lessons`, `academy_modules`, `academy_attestations`, `academy_assignments`, `academy_cycles`, `academy_certificates`, etc.).
- **`accounts`** - `public.accounts` is the 12-kitchen roster (team_key PK), owned by Directory. Academy must NOT reuse; if it needs a per-learner account concept, use something like `academy_enrollments`.
- **`contacts`** - Directory-owned people index. Distinct from `people` (Rippling roster). Academy learner-identity should key off `people.worker_id` or `user_accounts_derived.email`, not add a third people table.
- **`submissions`** - the People-submissions fact table (223 rows). If Academy wants "attestation submissions" or "quiz submissions", it must NOT reuse this name.

**No collisions** found for: `attestations`, `signatures`, `certificates`, `training*`, `obligations`, `nudges`, `checks`, `cycles`, `assignments`, `magic_links`, `email_bounces`, `notifications`. All safe to claim in `public.` (though `academy_*` prefix is recommended for discoverability, per the pattern OPD used).

## Contradictions with the prompt's Section 1 facts

- **`user_accounts` is NOT a table.** The prompt lists `user_accounts, user_accounts_derived, user_accounts_manual`. The `user_accounts` table was **dropped 2026-08-28** via `docs/migrations/user-accounts-table-drop.sql`. Only `user_accounts_derived` (VIEW, 35 rows) and `user_accounts_manual` (BASE TABLE, 3 rows) exist today. If Section 1 treats `user_accounts` as a live table, that's stale by ~3 days. The only production reader was cut over to `user_accounts_derived` in `#866` (2026-08-27); see `src/app/api/service-calendar/route.js:420`.
- **`rippling_raw_workers_latest` is a VIEW, not a table.** Live snapshot count is 1129 (same as `people.rows`, which is expected because `people` is derived from this view). Section 1 lumping it with tables is fine descriptively but the shape matters for anyone thinking they can INSERT into it.
- **`public.users` is present but empty (0 rows) and dead.** Not referenced by any code and no `CREATE TABLE users` in `docs/migrations/`. Section 1 didn't ask about it but Academy planners should know before naming things.
- **No academy-adjacent tables exist yet.** Section 1's list of "Anything with `attestation*`, `signature*`, `cert*`, `credential*`, `training*`, `obligation*`, `check*`, `question*`, `cycle*`, `assignment*`, `nudge*`, `magic_links`, `email_bounces`" yielded zero hits. The DB is greenfield for Academy in the `public` schema.

## Security note (surfaced per Supabase advisor)

The Supabase MCP `list_tables` call returned a critical advisory: **76 public tables have RLS disabled**. This is the intentional posture documented across the migration files (service_role bypasses RLS; auth is app-layer in `src/lib/opdAcl.js` and NextAuth). Every OPD table (`documents`, `document_relationships`, `document_surfaces`, `document_issues`, `document_pins`, `document_content`, `document_chunks`, `sousai_questions`) has RLS disabled by design per `pr-7-1` header comment and the same-shape header in `pr-8-1`. `sousai_questions` additionally has zero grants to `anon` / `authenticated` (service-role-only). If Academy will expose learner-visible surfaces client-side (via the Supabase JS client with the anon key), it must EITHER go through service-role API routes like every current module does, OR enable RLS with policies on any Academy tables it creates. The current app-layer pattern is the safer default; Academy tables should follow the same pattern unless a specific reason to deviate is documented.
