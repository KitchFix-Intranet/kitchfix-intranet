## The new project direction in one paragraph

KitchFix's Google Sheets backend has reached its architectural limit. R12 (rate limit) fired live yesterday. Dead-code accumulation is structural, not just a bug. We're migrating to Supabase (Postgres) via a strangler-fig staged approach. Stage 0 (current) is auditing the codebase and building a clean data-access abstraction layer that decouples API routes from the underlying storage. Once Stage 0 is complete, we set up Supabase (Stage 1), then migrate one data category at a time: read-only HUB config first (Stage 2a, lowest risk), then People Portal forms (2b), then Ops Hub transactional data (2c), then Service Calendar (2d). Estimated 3-5 months calendar time. Feature work is paused during migration except for the Pre-Service Briefing Tool which can be built against the abstraction once it exists.

1. **The audit work is real work, not preamble.** Don't rush to "actual migration code." The audit IS the migration prep, and rushing it creates schema design mistakes downstream.

3. **The "DO NOT TOUCH" list is sacred.** Touching anything related to `incidents` could break a feature actively being developed. When in doubt, leave it alone and ask Kevin.
